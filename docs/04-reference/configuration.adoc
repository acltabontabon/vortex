= Configuration reference: vortex.yaml
:toc:
:toclevels: 3

The portable definition of what to test. Commit it alongside the service it describes: a performance
definition that exists only inside one installation of a tool cannot be reviewed in a pull request,
run from a pipeline, or trusted to still describe what was measured last month.

A complete, heavily commented example lives at
`examples/checkout-service/.vortex/vortex.yaml`. Check any file with:

[source,bash]
----
vortex validate path/to/service
----

'''

== Shape

[source,yaml]
----
version: 1

service:        # what is under test
operations:     # how to issue each interaction
environments:   # where tests can run, and what those places are
thresholds:     # project-wide objectives
workloads:      # the workloads Vortex can apply
production:     # what the service actually receives today
observation:    # where production traffic can be fetched from
lab:            # the Compose file that starts this service's dependencies locally
----

Every section is optional except `version`, though a project with no `workloads` and no
`environments` cannot run anything.

'''

== `version`

[source,yaml]
----
version: 1
----

Version 1 described journeys and a project-wide traffic mix. It is *not* readable by this build and
is not migrated: a one-step journey would translate cleanly to an operation, but a multi-step one
would force Vortex to choose between discarding the sequence and reinterpreting an ordered flow as a
concurrent mix, and those mean different things. Loading a v1 file prints the edit required. See
xref:../adr/adr-024-service-level-workload-modelling.adoc[ADR-024].

'''

== `service`

The system under test: one deployable service.

[source,yaml]
----
service:
  name: checkout-service
  description: "Order placement and lookup for the storefront."
  version: 3f97a82
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `name` | string | The service, as its owners call it
| `description` | string | What it does
| `version` | string | The release under test — a commit, tag or build number. Optional
|===

=== `version`

Which build of *your service* these results describe — not the Vortex version.

A run that cannot name its build can still be read, but it cannot be compared with the next one:
"p95 rose by 20%" says nothing useful without knowing what changed between the two runs.

Set from `service.version`, below, or left absent. Absent stays absent — Vortex will not substitute
"unknown", because a placeholder that looks like a version is worse than an admitted gap.

The release is deliberately *not* part of experiment identity: two runs of the same experiment
against different releases are the comparison Vortex exists to make, so varying it must never make
two runs incomparable. See
xref:../02-architecture/execution-and-evidence.adoc#experiment-identity[experiment identity].

Dependencies are deliberately not listed here. They affect the numbers, but what they change is
_what a result may claim_, and that is modelled by the environment's `dependencies` and
`capabilities` instead.

'''

== `operations`

How to issue each interaction: request data, what a good answer looks like, and whether a person has
approved it.

The operations themselves come from an imported API description and are not repeated here, so
re-importing a specification never discards these decisions.

[source,yaml]
----
operations:
  createOrder:
    body: '{"accountId":"acc-1001","amount":42.5}'
    reviewed: true
    expect:
      status: [200, 201]
  getOrder:
    pathValues:
      id: "ord-1"
    headers:
      X-Tenant: "acme"
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `pathValues` | map | Values substituted into `{placeholders}` in the path
| `queryValues` | map | Query parameters
| `headers` | map | Headers for this operation alone, layered over the environment's. May contain `${SECRET}` references
| `body` | string | Request body, overriding the schema-generated default
| `bodyValues` | map | Individual body fields bound over that document, by name
| `expect.status` | list of int | Acceptable status codes; becomes a k6 `check()`. Default: anything that is not a server error
| `reviewed` | boolean | Whether a person has approved this operation's request data for execution
|===

=== Where a value comes from

Everywhere a value appears above — a header, a path value, a query value, a body field — it is
either written out or it says where it comes from.

A plain scalar is a *fixed* value, and a scalar containing `${NAME}` is read from the *environment*.
That is exactly the rule header values have always followed, so a file written before request-data
support keeps working unchanged and unmigrated. There is no `version:` bump.

Anything else is a mapping whose first key names the source:

[source,yaml]
----
operations:
  createApplication:
    reviewed: true
    headers:
      x-client-id: "lending-web"                       # fixed
      Authorization: "Bearer ${API_TOKEN}"             # environment
      x-idempotency-key: { generated: uuid }
      x-session: { generated: random-string, lifecycle: per-vu, length: 16 }
    pathValues:
      id: { dataset: customers, field: customerId }
    queryValues:
      channel: "web"
    body: '{"customerId":"","productCode":"","submittedAt":""}'
    bodyValues:
      customerId:  { dataset: customers, field: customerId }
      productCode: "CREDIT_CARD"
      submittedAt: { generated: timestamp }
    expect:
      status: [200, 201]
----

[cols="1,3", options="header"]
|===
| Form | Meaning

| `"a literal"`
| A fixed value.

| `"${NAME}"`
| Read from the environment variable `NAME` when the load generator starts. May be part of a larger
string, as in `"Bearer ${API_TOKEN}"`.

| `{ fixed: "..." }`
| A fixed value that genuinely contains `${...}` and must not be resolved. The only reason this form
exists.

| `{ generated: <name> }`
| Produced by Vortex. One of `uuid`, `timestamp`, `date`, `random-integer`, `random-string`,
`email`, `phone`, `sequence`.

| `{ dataset: <name>, field: <column> }`
| A field of the current row of a dataset. Add `scope: portable` for a dataset committed with the
service; the default is a dataset held on this machine.

| `{ environment: NAME }`
| The explicit form of `"${NAME}"`, for when the whole value is the variable.
|===

Generated values take two optional keys. `lifecycle:` is `per-request` (the default — a new value
for every request) or `per-vu` (one value per virtual user, held for that user's whole run).
`random-integer` reads `minimum:` and `maximum:`; `random-string` reads `length:`.

*Body fields are named, not addressed by expression.* A field path is one or more names joined by
dots — `customerId`, `payment.card.token` — at most eight levels deep. There are no array indices,
wildcards or filters: a body needing an array element should be supplied whole as `body`, with the
varying scalars bound around it.

*Datasets are not declared here.* Which datasets a service uses is derived from the values that name
one, and where each lives is the `scope` written on the value. Record counts, column names and
content hashes are read from the file itself — a count copied into this file would be accurate right
up until somebody edited the CSV. A portable dataset lives at `.vortex/datasets/<name>.<csv|json>`.

See xref:../03-performance-model/workloads.adoc#sources[test data] for what each source means and
how dataset rows are chosen, and
xref:../adr/adr-036-request-data-is-declared-not-scripted.adoc[ADR-036] for why the set is closed.

*`reviewed` is a safety gate.* An operation that changes data will not run without it. Schema-valid
is not business-valid, and creating records at a hundred a second should not become possible by
accident. It lives in this file rather than a local database on purpose: an approval visible in a
pull request is stronger evidence than a click in somebody's browser.

'''

== `environments`

Where tests can run, and — just as importantly — what each place actually is.

[source,yaml]
----
environments:
  local:
    type: LOCAL_ISOLATED
    baseUrl: "http://localhost:8080"
    dependencies: MOCKED
    capabilities:
      usesMockDependencies: true
      usesLocalStack: false
      productionLikeInfrastructure: false
      sharedEnvironment: false
      distributedExecutionAllowed: false

  performance:
    type: PERFORMANCE
    baseUrl: "https://checkout.perf.example.com"
    dependencies: REAL
    capabilities:
      productionLikeInfrastructure: true
      sharedEnvironment: true
      distributedExecutionAllowed: true
    headers:
      Authorization: "${VORTEX_AUTH_TOKEN}"
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `type` | enum | `LOCAL_ISOLATED`, `SHARED_TEST`, `PERFORMANCE`, `STAGING`, `CUSTOM`. Authoritative — Vortex never infers this from a hostname
| `baseUrl` | string | Where traffic goes
| `dependencies` | enum | `REAL`, `MOCKED`, `MIXED`, `UNKNOWN`
| `capabilities` | map | What the environment can support. `dependencies: REAL` *and* `productionLikeInfrastructure: true` together are what let a result be treated as integrated capacity evidence
| `headers` | map | Sent with every request
|===

*Secrets.* A header value of the form `${NAME}` is stored as a *reference*. Vortex resolves it from
the process environment when it launches the load generator, and nowhere else — it never reaches this
file, the execution history, the reports or the AI prompts.

'''

== `thresholds`

The objectives every run is judged against, unless a workload overrides them.

[source,yaml]
----
thresholds:
  latency:
    p95: 500ms
    p99: 1s
  errorRate:
    maximum: 1%
  perOperation:
    createOrder:
      latency:
        p95: 800ms
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `latency.p<n>` | duration | Maximum acceptable latency at that percentile
| `errorRate.maximum` | percentage | Maximum acceptable share of failed requests
| `perOperation.<id>` | same shape | The same objectives, scoped to one operation
|===

Without objectives a run produces measurements but no verdict, and a run with no verdict is a
demonstration rather than evidence.

*An objective that could not be checked is reported as not evaluated, never as passed.* That includes
an operation-scoped objective whose operation issued no requests.

'''

== `workloads`

The workloads Vortex can apply. This is the section you will edit most.

[source,yaml]
----
workloads:
  production-peak:
    type: STRESS
    description: "The workload the service receives at month-end settlement."
    objective: "Confirm the service sustains its observed production peak."
    shape:
      model: arrival-rate
      rate: 120
      duration: 30m
    source:
      kind: PRODUCTION_OBSERVED
      detail: "Grafana · rolling 30 days"
      observedAt: 2026-08-01T09:00:00Z
    operations:
      createOrder: 15
      getOrder: 25
      getOrderStatus: 55
      cancelOrder: 5
    thresholds:
      perOperation:
        getOrderStatus:
          latency: { p95: 200ms }
    k6:
      gracefulStop: 60s
----

=== `type`

The kind of performance question this workload asks:

[cols="1,3", options="header"]
|===
| Value | The question it answers

| `SMOKE` | Is the workload itself valid and can Vortex reach the service?
| `AVERAGE_LOAD` | Does the service meet its objectives under the traffic it normally receives?
| `STRESS` | How does it behave at or above its expected peak?
| `SPIKE` | How does it react to a sudden jump in demand?
| `SOAK` | Does performance degrade during sustained load?
| `BREAKPOINT` | At what level does it stop meeting its objectives?
|===

A test type is *intent*. It selects no executor and constrains no workload shape.

=== `shape`

How the load is produced. Two independent choices: the model, and whether the level is held or moved.

*Arrival rate, held steady:*

[source,yaml]
----
shape: { model: arrival-rate, rate: 120, duration: 30m }
----

*Arrival rate, ramping:*

[source,yaml]
----
shape:
  model: arrival-rate
  startRate: 10
  stages:
    - { target: 50,  duration: 5m }
    - { target: 100, duration: 5m }
----

*Concurrency, held steady:*

[source,yaml]
----
shape: { model: concurrency, vus: 50, duration: 10m }
----

*Concurrency, ramping:*

[source,yaml]
----
shape:
  model: concurrency
  startVUs: 10
  stages:
    - { target: 25, duration: 5m }
    - { target: 50, duration: 5m }
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `model` | enum | `arrival-rate` (open) or `concurrency` (closed). Default `arrival-rate`
| `rate` | number | Requests per second, *total across every operation*
| `vus` | integer | Concurrent virtual users
| `duration` | duration | How long to hold it. Max 24 hours
| `startRate` / `startVUs` | number | Where a ramp begins. Defaults to the first stage's target
| `stages` | list | `{ target, duration }` — each stage is one observation of "did it still meet its objectives here?"
|===

Choose the model that matches the real caller. Arrival rate offers a fixed number of requests per
second whatever the service does — the usual choice, because it holds the pressure steady exactly
when the service starts to slow. Concurrency holds a fixed number of clients each waiting for its
previous request, which is honest when the caller really is a bounded pool. See
xref:../03-performance-model/workloads.adoc[arrival rate vs concurrency].

=== `operations`

The traffic composition: which operations are exercised and in what proportion.

[source,yaml]
----
operations:
  createOrder: 15
  getOrder: 25
  getOrderStatus: 55
  cancelOrder: 5
----

Weights are relative, so `15/25/55/5` and `3/5/11/1` mean the same thing. The workload supplies one
*total* and Vortex divides it — it never runs each operation at the full total. At 120 requests/sec
the mix above allocates 18 / 30 / 66 / 6.

*One operation is a complete workload:*

[source,yaml]
----
operations: { createOrder: 100 }
----

*A weighted mix requires an arrival-rate workload.* Under concurrency the weights would divide
virtual users, and a virtual user's throughput depends on how fast its operation responds — so 25% of
the VUs is not 25% of the requests, and the two drift further apart as the service degrades. A
concurrency workload therefore targets exactly one operation.

This is composition, not a sequence: it describes concurrent traffic from many callers, not one
caller working through several endpoints in order. See
xref:../03-performance-model/workloads.adoc[composition vs sequence]. This is also the canonical
instance of the `createOrder`/`getOrder`/`getOrderStatus`/`cancelOrder`, 120 requests/sec, 15/25/55/5
example used throughout this documentation set — other documents illustrating the same point refer
back here for the full configuration.

=== `source`

Where the numbers came from.

[source,yaml]
----
source:
  kind: PRODUCTION_OBSERVED
  detail: "Grafana · checkout-service overview · rolling 30 days"
  observedAt: 2026-08-01T09:00:00Z
----

`kind` is `PRODUCTION_OBSERVED`, `DERIVED_FROM_OBSERVATION` or `MANUAL` (the default). Shown beside
the figure everywhere it appears, because "50 requests/sec" means something different depending, and
a capacity conclusion inherits the confidence of its weakest input.

=== `thresholds`

Same shape as the project-level section. Layered over the project defaults by objective, so a
workload can refine `p95` without restating the error rate.

=== `k6` — the escape hatch

Raw k6 scenario options, merged verbatim into every k6 scenario this compiles to:

[source,yaml]
----
k6:
  gracefulStop: 60s
  maxVUs: 500
----

Applied last, so an override wins over anything Vortex chose. Deliberately unvalidated: Vortex does
not model k6's option schema, and pretending to would create a second, always-stale copy of it. k6
rejects what it does not understand, and preflight reports that before any traffic is generated.

'''

== `production`

What the service actually receives today. This is what turns an invented traffic number into a
production-informed one, and it is the only basis on which Vortex will calculate capacity headroom.

[source,yaml]
----
production:
  observedAverage: 45      # requests per second
  observedP95Rate: 95      # the 95th percentile of request RATE, not latency
  observedPeak: 120
  observedMix:
    createOrder: 15
    getOrder: 25
    getOrderStatus: 55
    cancelOrder: 5
  mixCoverage:
    observedRequests: 100000
    matchedRequests: 80000
  sampleResolution: 1h
  source: "Grafana · checkout-service overview · rolling 30 days"
  observed:
    from: 2026-07-02T09:00:00Z
    to: 2026-08-01T09:00:00Z
  provenance:
    provider: prometheus
    query: "max_over_time(sum(rate(http_server_requests_seconds_count{application=\"checkout-service\"}[3600s]))[2592000s:3600s])"
    entity: checkout-service
    url: "http://prometheus.internal:9090/graph"
  note: "Peak observed during the month-end settlement window."
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `observedPeak` | number | Required. Highest observed request rate
| `observedAverage` | number | Observed mean request rate across the window
| `observedP95Rate` | number | 95th percentile of the sampled request *rate*
| `observedMix` | map | How that traffic is distributed across operations
| `mixCoverage` | map | How much of the observed traffic that mix accounts for
| `sampleResolution` | duration | The interval each rate sample averaged over
| `source`, `observed`, `note` | | Provenance, recorded so a stale or unattributed figure is visible as such
| `provenance` | map | Which system answered and the query it was asked, when the observation was fetched
|===

=== Every rate here is a rate

`observedP95Rate` is the 95th percentile of your service's *request rate* across the observation
window. It is not a response-time percentile, and the distinction is not pedantry: this figure sits
a few lines away from a `thresholds.latency.p95` objective, and a reader who conflates the two
calibrates a workload from entirely the wrong number.

The key was previously spelled `observedP95`. That spelling is still read, so a committed file keeps
loading; Vortex writes the new one.

Observed *latency* percentiles are deliberately absent. Nothing in calibration or headroom consumes
them, and this section holds only what those two actually use.

=== The composition matters as much as the volume

120 requests/sec of cheap status polling is a different workload from 120 requests/sec of order
submission. Vortex will propose workloads from an observation, and it *refuses* to propose them from
a volume with no `observedMix` — a workload built on a guessed distribution would carry the authority
of production evidence without any of the evidence.

=== `mixCoverage` — how much of production the mix describes

A mix normalises: three operations carrying 50%, 30% and 20% of *matched* traffic are stored as
50/30/20 whatever share of production they represent between them. That is what a mix is — it
describes shape, and shape has to sum to one. On its own it is also how a partial match silently
becomes a claim about the whole service.

So the two raw counts are kept beside it. If Vortex matched 80 of every 100 requests to a known
operation, the mix describes 80% of production and says so. Below 80%, `vortex calibrate --apply` and
the web *Create these workloads* button both refuse, naming what could not be attributed.

The unmatched share never becomes a synthetic "other" operation. Vortex can only issue requests
against operations in the service catalog, so an invented entry would produce a workload it cannot
run — while implying the traffic had been understood.

*Narrowing the evidence is acceptable. Overstating its completeness is not.*

'''

== `observation`

Where Vortex can go and ask what the service receives, so the numbers in `production` can be fetched
rather than remembered. Optional: an observation typed in by hand is a perfectly good starting point,
and this section only changes where it comes from.

[source,yaml]
----
observation:
  source: prometheus
  endpoint: http://prometheus.internal:9090
  service: checkout-service          # the value of the service label
  window: 30d
  headers:
    Authorization: "Bearer ${PROM_TOKEN}"
  labels:                            # only if not using Micrometer's defaults
    service: application
    route: uri
    method: method
----

[source,yaml]
----
observation:
  source: dynatrace
  endpoint: https://abc12345.live.dynatrace.com
  entity: SERVICE-1A2B3C4D5E6F7890
  window: 30d
  headers:
    Authorization: "Api-Token ${DT_TOKEN}"
----

[source,yaml]
----
observation:
  source: dynatrace
  transport: mcp                       # reach Dynatrace through the MCP endpoint configured
  entity: SERVICE-1A2B3C4D5E6F7890      # under Settings, instead of this endpoint/headers pair
  window: 30d
----

[cols="1,1,3", options="header"]
|===
| Key | Type | Meaning

| `source` | enum | Required. `prometheus` or `dynatrace`
| `transport` | enum | `rest` (default) or `mcp` — Dynatrace only. See <<dynatrace-via-mcp,Dynatrace via MCP>>
| `endpoint` | url | Required unless `transport: mcp`. The API root, not a dashboard URL
| `service` | string | Required for Prometheus. The value of the service label
| `entity` | string | Required for Dynatrace. The entity id, e.g. `SERVICE-1A2B3C4D5E6F7890`
| `window` | duration | Required. How far back to look, e.g. `30d`
| `headers` | map | Request headers. Values may be `${NAME}` references. Ignored when `transport: mcp`
| `labels` | map | Prometheus label names for `service`, `route` and `method`. Ignored by Dynatrace
|===

Credentials work exactly as a target's authorisation header does: write `${NAME}`, and Vortex stores
the reference and resolves it from the environment only at the moment it issues a request. The value
never reaches this file, the database, a report or an AI prompt. A reference naming a variable that
is not set is reported before anything is sent, rather than silently producing an anonymous call.

=== Configured from the interface, or by hand

The Configuration tab has a *Where to fetch production traffic from* card that writes this section,
with a *Test connection* button beside it. The test asks one question — the peak over the window —
which is enough to prove three things that fail independently: the endpoint is reachable, the
credentials are accepted, and the service identifier matches something the system has actually seen.
It reports the number it saw rather than a green tick, because "connected" would also pass against a
Prometheus that has never heard of this service.

Neither saving nor testing fetches an observation. Naming a monitoring system and asking it for a
month of traffic are separate acts.

=== Two sources, not a plugin framework

Prometheus and Dynatrace are systems teams actually run, and two real adapters written against them
are worth more than an extension point with two names attached to it. A third becomes worth building
when somebody has one and needs it.

OpenTelemetry is not a third source. It is how a service *emits* telemetry, not something Vortex
queries: a service instrumented with it is already reachable through whichever system ingests it.
Vortex will not build a collector or a telemetry pipeline of its own.

[[dynatrace-via-mcp]]
=== Dynatrace via MCP

Some teams' only route to Dynatrace is an internally-managed MCP server, often reachable only over
a corporate VPN and with no separate credential — the VPN is the perimeter. `transport: mcp` on a
Dynatrace source points Vortex at that server instead of Dynatrace's REST API, without changing
anything else about how `observation`, `production` or calibration behave.

*What it does not do.* Vortex connects to the MCP endpoint directly over HTTPS, as a full MCP
client. A config for it is often shaped for a different kind of client and looks like this:

[source,json]
----
{"dynatrace": {"command": "npx", "args": ["mcp-remote", "https://dynatrace-mcp.internal/mcp"]}}
----

`mcp-remote` is a local bridge for MCP clients that only speak stdio. *Vortex never runs it* — it is
not that kind of client. If you paste this exact shape into Settings → Dynatrace, Vortex recognises
it, extracts the URL, and shows it for review before anything is saved; it never executes the
command. A bare `{"url": "...", "headers": {...}}` entry — the shape an editor-integrated MCP
client produces — is recognised the same way. Anything Vortex cannot reduce to "here is the remote
URL" is refused with an explanation rather than run.

*Setup.*

1. Get the MCP endpoint URL from whoever manages your Dynatrace access — either the bare URL, or
   their `mcp-remote`-shaped config.
2. Under *Settings → Dynatrace*, paste the config (or enter the URL directly) and *Save*.
3. *Test connection* — this checks the endpoint is reachable, authentication succeeds if a
   credential is configured, and the server offers the `execute_dql` tool Vortex needs.
4. On a service's Configuration page, under *Production reality*, set the source to Dynatrace and
   *Connect via* MCP, and give the service's entity id — see *Finding the entity id* below.

*Finding the entity id.* Under *Configure source*, *Look up entity id by name* (pre-filled with the
service's own name in Vortex, editable) tries to resolve a matching Dynatrace entity for you — pick
a result to fill in the id below it, or keep typing the id in by hand regardless of what the lookup
finds; a lookup result is only ever a suggestion. This needs a working Dynatrace MCP connection, so
it isn't available when *Connect via* is REST, and it can find nothing if the name in Dynatrace
doesn't resemble the one in Vortex closely enough. Either way, the entity id can always be found by
hand: open the service in Dynatrace directly — its id (starting with `SERVICE-`) is in the URL and
under Properties. See docs/adr/adr-058-dynatrace-entity-lookup-by-name.adoc.

*Authentication.* Dynatrace's MCP endpoint accepts a bearer token from either of two mechanisms:

* *Bearer header* (default) — a static, long-lived platform token, pasted as an
  `Authorization: Bearer ${NAME}` header exactly like any other header value.
* *OAuth client credentials* — a client ID and secret exchanged for a short-lived access token
  Vortex fetches and refreshes on its own, with no browser involved. Enter the client ID, secret,
  scope and resource under *Settings → Dynatrace*; the secret follows the same `${NAME}`
  environment-reference convention as a header value.

A config generated by an editor-integrated MCP client (a bare URL with no headers) implies a third
mechanism — an *interactive* OAuth login through a browser. Vortex does not implement that flow
itself: over *Direct HTTPS* connection mode, pasting such a config will show the URL but
authentication will fail; replace it with a platform token or a separately-obtained OAuth
client-credentials client instead. If neither of those is available to you, see
<<dynatrace-via-mcp-local-bridge,Connecting through a local bridge instead>> below.

[[dynatrace-via-mcp-local-bridge]]
*Connecting through a local bridge instead.* Under *Settings → Dynatrace*, *Connection mode* can be
set to *Local bridge (npx mcp-remote)* instead of *Direct HTTPS*. In this mode Vortex spawns
`npx mcp-remote <endpoint>` locally and lets it perform Dynatrace's interactive OAuth login itself —
the first connection opens a system browser to sign in, and the resulting session is cached and
reused (and refreshed) afterward without a browser. *Authentication* above and the header/OAuth
fields are not used in this mode; `mcp-remote` manages its own credential entirely.

This needs Node.js (for `npx`) and a browser *on the same machine Vortex runs on*, so it only makes
sense for a local, single-machine install — it does not help a shared or headless deployment, and
Vortex does not pretend otherwise. It is also slower per connection than Direct HTTPS (a process
starts for every call) and, unlike the direct paths, Vortex cannot always guarantee the spawned
process is terminated if it does not exit cleanly on its own. Prefer a platform token or an OAuth
Client Credentials client whenever either is available; reach for the local bridge only when neither
is. See docs/adr/adr-051-dynatrace-mcp-local-npx-bridge.adoc for the full reasoning.

*What travels to Dynatrace.* Only three fixed, versioned queries — throughput, request latency and
failure rate, each a hand-written DQL statement Vortex composes itself. Nothing asks Dynatrace or
any MCP tool to interpret, summarise, or decide what a baseline means; that stays Vortex's own
`ProductionObservation` calculation, identical to the REST path.

*Known limitation.* Operation mix (the per-endpoint traffic breakdown) is not yet available over
MCP — `production.observedMix` is absent for an MCP-sourced observation, the same as it would be for
a REST-sourced one Dynatrace could not attribute.

*Troubleshooting.*

[cols="1,3", options="header"]
|===
| Test connection fails at | Usual cause

| OAuth token obtained | Only shown in OAuth client credentials mode — the client ID or secret is wrong, or the client isn't authorized for the given scope/resource
| Local bridge started | Only shown in local bridge mode — `npx`/Node.js isn't installed, or `mcp-remote` is waiting on a browser login; open the URL shown and try again
| MCP server reachable | Not on the VPN, or the endpoint URL is wrong
| Authentication | The credential referenced under Settings is unset or wrong
| Dynatrace tool discovered | The server does not offer `execute_dql` — check with whoever manages it
|===

A passing *Test connection* only confirms the shared MCP connection works — it does not check a
specific service's entity id or whether Dynatrace has traffic for it. If a run reports no data once
a service is mapped, check the entity id and the observation window instead.

=== What each number means

Every rate Vortex takes from a monitoring system is a statistic *of a set of samples*, and the sample
interval decides what the word means. A peak from one-minute samples is the busiest minute; a peak
from hourly samples is the busiest hour, which is a smaller number describing the same traffic.

The interval therefore scales with the window, by a stated rule, and travels back with the
observation as `sampleResolution`:

[cols="1,2", options="header"]
|===
| Observation window | Sample resolution

| up to 2 days | `1m`
| up to 14 days | `5m`
| beyond | `1h`
|===

A thirty-day window at one-minute resolution is forty-three thousand points, which most Prometheus
deployments will refuse to evaluate and no engineer needs.

For Prometheus, against a request counter `C` over window `W` at resolution `r`:

[cols="1,2,2", options="header"]
|===
| Statistic | Expression | What it means

| peak | `max_over_time( sum(rate(C[r]))[W:r] )` | highest `r`-averaged request rate seen in `W`
| p95 rate | `quantile_over_time(0.95, sum(rate(C[r]))[W:r])` | 95th percentile of those same samples
| average | `sum(increase(C[W])) / W` | total requests over `W` divided by `W`
|===

The average deliberately does not use `avg_over_time` of a rate subquery: `rate()` extrapolates at
series boundaries, so averaging its samples drifts from the true mean, while total requests divided
by elapsed time is the definition of one. Peak and p95 are statistics of the *same* sample set, which
is what makes them comparable to each other.

The expression as issued is recorded in `production.provenance`, so any figure can be checked against
the system that produced it.

=== Fetching never writes

`vortex calibrate` prints what it found and the workloads it would propose. It records nothing unless
asked with `--write`, and creates no workloads unless asked with `--apply`. The web interface behaves
the same way: *Fetch* populates the review form, and the existing *Record observed traffic* form
stays the only thing that writes.

The reason `vortex.yaml` is in version control is that somebody can review a change to it. A
calibration that edited it on its own would be a change nobody saw.

== `lab`

The Compose file that starts this service's dependencies on a developer's machine.

[source,yaml]
----
lab:
  compose: compose.yaml
----

[cols="1,1,3", options="header"]
|===
| Field | Type | Meaning

| `compose` | path | The Compose file, relative to this repository
|===

Optional, and absent is the ordinary case for a service with no dependencies. Vortex runs the file
your repository already owns — it does not generate one, and it does not manage anything else about
Docker. See xref:../02-architecture/architecture.adoc#local-lab[local lab].

=== The path is relative, and Vortex insists

`vortex.yaml` is committed and read on other people's machines, so an absolute path is refused with
an explanation rather than stored. Paths that climb out of the repository are refused for the same
reason.

What is stored is the normalised form: writing `./infra/../compose.yaml` saves `compose.yaml`, so one
path has one spelling in the committed file.

=== Starting dependencies is always explicit

Recording this setting starts nothing, and no run starts it either. A developer presses *Start
dependencies* on the service's settings page, and Vortex reports what the Compose command did.
Vortex does not watch the containers afterwards, and a successful start is never treated as evidence
that the service is healthy or ready to test.

== There is no configuration schema

Not yet. `vortex.yaml` itself is defined by `YamlConfigurationStore`, which parses by hand so that
every rejection can name the field, say what was wrong, and say what to do instead — a validation
error that says only "invalid configuration" makes you hunt for a problem Vortex has already located.
A published JSON Schema for `vortex.yaml` is reserved for when the format settles.

This is a statement about configuration, not about evidence: the *output* of a run has a published
schema today, at xref:../schema/vortex-evidence-v2.schema.json[the `vortex.evidence/2` schema].

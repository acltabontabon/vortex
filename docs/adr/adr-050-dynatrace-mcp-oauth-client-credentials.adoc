= ADR-050: Dynatrace MCP authenticates via a static header or OAuth client credentials, never an
interactive browser flow

== Status

Superseded by xref:adr-052-dynatrace-mcp-bridge-only.adoc[ADR-052] — the header and OAuth Client
Credentials auth modes this ADR added, and the direct-HTTPS client they authenticated, were removed;
the local npx/mcp-remote bridge from ADR-051 is now the only connection mode. Kept for the reasoning
behind the header-vs-OAuth choice while it existed.

== Context

ADR-049 gave Vortex a direct, header-authenticated MCP client for Dynatrace. In practice, a
Dynatrace MCP endpoint accepts a bearer token obtained three different ways:

1. **Platform token** — a static, long-lived token issued once from Dynatrace's Account Management
   UI. Already fully supported: paste it as an `Authorization: Bearer ${NAME}` header exactly like
   any other header value. No code changes needed.
2. **OAuth, Authorization Code grant** — interactive: the MCP client opens a browser, the person
   using it logs into Dynatrace SSO, and the client catches a local redirect callback. This is what
   editor-integrated MCP clients (that generate a bare `"url"` config with no headers) trigger by
   default.
3. **OAuth, Client Credentials grant** — machine-to-machine: a client ID and secret are exchanged
   directly for a short-lived access token, no browser involved.

A config generated for an interactive editor client is shaped like option 2 — a bare URL, no
headers — and saving it into Vortex as-is fails at authentication, because Vortex is a headless
service with no person available to complete a browser login at connection time. That failure is
not a bug to route around; it means the config was built for the wrong kind of client.

Separately (a plain parser gap, not an auth decision): `DynatraceMcpConfigImport` recognised only
the `npx`/`mcp-remote` stdio-bridge shape from ADR-049 and returned "unrecognized" for a bare
`{"url": "...", "headers": {...}}` entry — the shape editor-integrated MCP clients actually produce
natively. Fixed alongside this work so pasting either shape extracts the URL for review.

== Decision

Vortex supports options 1 and 3. Option 2 is explicitly out of scope: there is no local OAuth
callback endpoint, no redirect URI handling, and no plan to add one. A headless backend service has
no "user in the loop" at connection time to complete a browser login, so replicating that flow would
be the wrong shape for the job, not a missing feature. A config that implies Authorization Code must
be replaced with a platform token or a separately-obtained Client Credentials client — Vortex says so
in its Settings UI and troubleshooting output rather than failing silently.

`DynatraceMcpSettings` gains an `AuthMode` (`HEADER` or `OAUTH_CLIENT_CREDENTIALS`) alongside
`clientId`, `clientSecret`, `scope`, and `resource`. `clientSecret` follows the same `${NAME}`
environment-reference and masked-round-trip discipline the existing header values already use — it
is itself a long-lived, externally-managed credential, unlike the short-lived access token it
produces.

A new `DynatraceOAuthTokenProvider` POSTs `grant_type=client_credentials` to
`https://sso.dynatrace.com/sso/oauth2/token`, caches the resulting access token in memory keyed by
the credential tuple, and re-requests a few seconds ahead of expiry — there is no refresh token to
manage; Client Credentials issues none. `DynatraceMcpClientFactory` resolves `clientSecret`, fetches
a token, and merges `Authorization: Bearer <token>` into the headers map *before*
`DynatraceMcpEndpoint`/`DynatraceMcpTelemetryClient` are touched, so those classes stay completely
unaware OAuth exists — from their side, it is just a header string, exactly as it was for a platform
token. The cached token is never written to disk, matching the standing invariant that a resolved
secret must never reach a plan, artifact, log, or prompt.

Testing the connection in OAuth mode adds a leading stage, "OAuth token obtained", ahead of the
existing MCP-reachability stages — SSO rejecting the client credentials is a distinct failure point
from the MCP server rejecting the token, and the two need to be distinguishable in the result.

== Consequences

A team whose only Dynatrace access is a Client Credentials OAuth client can now use Vortex without
a platform token. A team that only has an editor-generated (Authorization Code) config gets a clear
answer for why it does not work and what to use instead, rather than a bare connection failure.

The cost is a second credential shape to carry through settings, storage, and the connection test,
and one more outbound HTTP call (to Dynatrace's SSO token endpoint) on the path to a working
connection. Both are additive: `AuthMode.HEADER` is unchanged in behavior, and an unconfigured
installation still starts, reports unavailable, and never fails to boot.

Reversible at low cost: `AuthMode.OAUTH_CLIENT_CREDENTIALS` and its supporting fields could be
removed without touching the header-authenticated path at all.

Interactive Authorization Code OAuth remains explicitly out of scope, as does client-secret rotation
beyond what re-saving Settings already provides.

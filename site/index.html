The paralysis of “it’s probably fine”

You own a service. You have a rough sense of its traffic. But you're not a performance-testing specialist, and neither is most of your team — so the honest answer to "will this hold up?" is usually a shrug.

The hard part was never running a load test. It's knowing what traffic to model, which thresholds actually matter, and how to read the wall of numbers a test produces afterward. Vortex exists to remove that paralysis.

How it works

  1. Service

    Pick the one service you're testing, so everything that follows stays focused on it.

  2. Workload

    Describe a realistic traffic condition once — version-controlled and reusable, not a throwaway script you'll rewrite next time.

  3. Evaluation

    State the actual question you care about: can it hold peak load? Where does it break?

  4. Run

    Run it.

  5. Evidence

    Get back a result and the exact conditions that produced it — traceable, comparable, and defensible when you show it to a colleague.

What makes the results trustworthy

A total is divided, never repeated.
Arrival rate and concurrency are never conflated.
Aggregate latency is never the whole story.
Capacity is always conditional.
Unevaluated is not the same as passed.

AI is optional, never load-bearing

Vortex is fully usable with no model at all. Every pass/fail answer it gives you is deterministic. An optional local AI layer can help interpret results in plain language afterward — but it's enrichment on top of the evidence, never a substitute for it.

Where things stand

Vortex is an early alpha — a working MVP, not a finished product. Some capabilities are still on the roadmap. We'd rather tell you what isn't done yet than let you find out the hard way; the GitHub repository tracks exactly where things stand.
